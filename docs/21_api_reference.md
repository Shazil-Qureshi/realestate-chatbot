Interactive documentation, generated by FastAPI from the code itself, is at
**[`/docs`](https://realestate-chatbot-4707.onrender.com/docs)** on the live
service. This page explains the behaviour behind it: what each field means,
what can go wrong, and why some of it is shaped the way it is.

| | |
|---|---|
| **Live** | `https://realestate-chatbot-4707.onrender.com` |
| **Local** | `http://127.0.0.1:8000` |
| **Format** | JSON in, JSON out, UTF-8 |
| **Authentication** | None. It is a public demo. |

The live service sleeps after 15 minutes without traffic. The first request
after that takes up to about a minute while it wakes.

## Who may call it

The browser will only let a page read a reply if that page's origin is on the
server's allow-list (`ALLOWED_ORIGINS`), which is the GitHub Pages site and
local development. Anything else gets a CORS error in the browser.

This is a browser rule, not a lock: `curl` and other tools ignore CORS
entirely. What actually limits abuse is the rate limiting below.

`Retry-After` is the only response header a page is allowed to read.

## Rate limits

Checked **before** any work is done, so a refused request costs no API quota.
See [18](18_rate_limiting.md).

| Limit | Default |
|---|---|
| `/chat` per visitor | 10 per minute, 100 per day |
| `/chat` everyone together | 500 per day |
| `/lead` per visitor | 5 per minute, 20 per day |

Requests from the same machine (`127.0.0.1`, `::1`) are not counted, so the
test suite is not throttled. Exceeding a limit returns **429** with a
`Retry-After` header and a plain-language message.

## GET /health

Whether the server is up, and what it is running. Not rate limited: the
hosting platform polls it, and the widget calls it on page load.

**200 — running**

```json
{
  "status": "ok",
  "prompt_version": "2026-11-25a (10 rules, near matches rule 10)",
  "chunks": 56,
  "chat_model": "gemini-3.5-flash-lite",
  "embedding_model": "gemini-embedding-2",
  "leads_go_to": "nowhere (demo mode: checked, then discarded)",
  "leads_demo": true,
  "rate_limits": {
    "enabled": true,
    "chat_per_minute": 10,
    "chat_per_day": 100,
    "chat_total_per_day": 500,
    "lead_per_minute": 5,
    "lead_per_day": 20
  },
  "area_filtering": 12
}
```

| Field | Meaning |
|---|---|
| `status` | `"ok"` when the index is loaded; `"starting"` while it still loads. The server answers immediately either way — it opens its port first and loads in the background, because the platform's health check will not wait ([16](16_render.md)). |
| `prompt_version` | Which system instruction is running. Changing the instruction without bumping this is how you end up testing yesterday's behaviour. |
| `chunks` | Pieces in the search index. `0` means ingestion failed. |
| `leads_go_to` | Says *where* leads go in words. It deliberately never contains the webhook address. |
| `area_filtering` | How many areas the index knows. `0` means the index predates Task 4.1 and area search is silently off ([20](20_area_filtering.md)). |

**503 — startup failed.** `{"detail": "Startup failed: ..."}`. The server is
running but unusable: no API key, a missing or empty index. The message says
which.

## POST /chat

Ask a question. Costs **two** Gemini calls: one to embed the question, one to
answer it.

**Request**

```json
{ "message": "What are your fees for buying a property?" }
```

| Field | Type | Rules |
|---|---|---|
| `message` | string | Required. Not blank. At most 1000 characters. |

**200**

```json
{
  "answer": "For buying a property, our commission is 1 percent of the sale price...",
  "sources": [
    {
      "heading": "Agency fees",
      "source": "data/company_info/02_services_and_fees.md",
      "distance": 0.1832
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `answer` | The reply, built only from the pieces retrieved for this question. |
| `sources` | The pieces used, up to 8. Shown in the widget so a visitor can see where an answer came from. |
| `distance` | Cosine distance. **Lower is closer.** Worth knowing: in the DHA case the *correct* listing came back at `0.2729`, the furthest of nine — which is exactly why area filtering had to exist ([20](20_area_filtering.md)). |

**Errors**

| Code | When | Example |
|---|---|---|
| 400 | Empty message | `{"detail": "The message is empty."}` |
| 400 | Over 1000 characters | `{"detail": "The message is too long. Limit is 1000 characters."}` |
| 429 | Rate limited | `{"detail": "Too many questions too quickly. Please wait 42 seconds and try again."}` |
| 503 | Still starting, after a 120 s wait | `{"detail": "The assistant is still starting. Try again in a minute."}` |
| 503 | Gemini or the index unreachable | `{"detail": "Could not reach the language model: ..."}` |

A 503 from Gemini is usually `UNAVAILABLE — experiencing high demand`, which is
an outage at Google, not a fault here. The test suite retries it rather than
reporting a failure.

## POST /lead

Pass an enquiry to a human. No Gemini call, so it costs no quota.

**Request**

```json
{
  "name": "Ayesha Khan",
  "phone": "0300 1234567",
  "email": "ayesha@example.com",
  "property_ref": "BRE-R-202",
  "message": "I would like to view this on Saturday.",
  "consent": true
}
```

| Field | Required | Rules |
|---|---|---|
| `name` | yes | 2–80 characters, must contain a letter |
| `phone` | yes | 10–15 digits. Spaces, dashes, brackets and a leading `+` are accepted and stripped |
| `email` | no | Must look like an address if given |
| `property_ref` | no | For example `BRE-R-202` |
| `message` | no | Up to 500 characters |
| `consent` | yes | Must be `true` |
| `website` | no | **Honeypot — always leave empty.** See below. |

**200**

```json
{ "status": "received", "lead_id": "7c15a05c05a2", "demo": true }
```

`demo: true` means the live service validated the details and then discarded
them. `lead_id` is a short reference; it is the only part of a lead that ever
appears in a log.

**Errors**

| Code | When |
|---|---|
| 422 | A field failed validation |
| 429 | Rate limited |

A 422 uses FastAPI's standard shape, so `detail` is a **list**, not a string —
one entry per field that failed:

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body", "phone"],
      "msg": "Value error, Enter a phone number with 10 to 15 digits, for example 0300 1234567.",
      "input": "abc"
    }
  ]
}
```

The wording after `Value error, ` is written for the visitor to read, not for a
developer: *"Enter your name."*, *"Details can only be sent once you have
agreed to share them."* The widget strips that prefix and shows the rest
beside the field.

Note that `input` echoes what was sent. That is fine here because it is the
visitor's own data coming back to their own browser, but it is a reason not to
log a 422 body anywhere.

### Two behaviours that look like bugs and are not

**A filled honeypot returns 200.** `website` is hidden from people by CSS, so
only a bot fills it. A bot that fills it gets a perfectly normal "received" —
and the lead is thrown away. Returning an error would simply teach the bot
which field gave it away.

**Consent is checked on the server.** The widget asks for it too, but anything
can post to this endpoint, so the widget's check is a courtesy and this one is
the rule.

### When n8n is unreachable

The chat keeps working. The lead is written to
`backend/leads/pending.jsonl` and the visitor is still thanked — from their
side nothing failed, because nothing about their request did. The log records
only the lead id.

Those queued leads are **not** re-sent automatically; that is a known gap
(LEAD-R1).

## Examples

**curl**

```bash
curl -s https://realestate-chatbot-4707.onrender.com/health

curl -s -X POST https://realestate-chatbot-4707.onrender.com/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Do you have 3-bedroom houses in DHA?"}'
```

**JavaScript**, as the widget does it

```javascript
const response = await fetch(`${API_URL}/chat`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ message: question }),
});

if (response.status === 429) {
  const { detail } = await response.json();
  show(detail);                                   // the server's own wording
  return;
}

const { answer, sources } = await response.json();
```

The widget retries only a status of 0 or 502/503/504, for up to 90 seconds,
because those mean the free tier is waking up. A 429 is never retried: the
server has already said how long to wait.
